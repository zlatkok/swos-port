Format of the team file (team.* in \data directory):

Size of the team structure used in files is 684 bytes. Maximum size of team
file is 64000 bytes, as that is the size of the fixed buffer SWOS uses,
anything above that will cause immediate SWOS termination. Inside the team
files teams seem to be sorted alphabetically.

First we have a word, big endian - number of teams in the file
then there is team header, 76 bytes
header is followed by 16 structures that represent players
size is 38 bytes each

There is another team structure, which is used during the game, and its size is
1704 bytes. We'll refer to it as in-game team.

offset:  size:  desc.
-------  -----  -----
                (converted colors)
                 primary set:

   2       2    shirt background color
   4       2    shirt stripes color
   6       2    shorts color
   8       2    socks color

  10       2    shirt type
  12       2    shirt background color
  14       2    shirt stripes color
  16       2    shorts color
  18       2    socks color
  20       2    marked player index (-1 if nobody was marked)
  22      17    team name, null terminated
  39       1    ?
  40       1    number of own goals
  41       1    ? - these 3 fields are always zero in hil files

Header size - 42 bytes.

  Ofs22 is tested in FixupAndColorPitchFile(), and if lower bit is set,
  team places are swapped

16 player structures follow the header:

offset:  size:  desc.
-------  -----  -----
   0       1    ? - always zero in hil files, but if it's not zero the player
                is skipped (arrow can't select it), probably isInjured flag
   1       1    player index in team file structure
   2       1    number of goals scored
   3       1    shirt number
   4       1    player position index, or -1 he was substituted
   5       1    player face index
   6       1    is player injured? [0,1]
   7       1    ?
   8       1    not sure what it is exactly, but if it's true player will spend
                only 25 frames on tackling instead of 55, although it's reset
                to -1 later in each case (wtf)
   9       1    this influences red card criteria, seems to be more strict if
                it's true
                might be true if player already has a yellow card?
                cards (offset 10) are copied here right before the game
  10       1    yellow/red card bit-flags:
                bit 0 - yellow card
                bit 1 - red card (direct, or via double yellow)
                range seems to be 0..4
  11       1    not sure what it is, but if it's negative the player can not be
                substituted -- that is only in the case bench state is 3, which
                never happens, so this might be unused
  12      14    player number + name (or first letter of name + surname) (string)
  26       1    probably zero terminator for field above
  27       1    passing (values 0..7)
  28       1    shooting
  29       1    heading
  30       1    tackling
  31       1    ball control
  32       1    speed
  33       1    finishing
  34       1    0..7, related to goalkeeper, index into a table of pointers
                which ends up written to TeamGeneralInfo ofs24
  35       1    OR with PlayerFile ofs103 & 0xff1f, bits 7,6 and 5 mean
                something - seems to be red cross blinking speed when a player
                is injured; if this is zero player is not injured; if whole
                field is not zero, and bit 5 isn't set, seems to be permanent
                injury
                5th bit marks serious injury (0x20)
                bits 5, 6 and 7 represent degree of injury, and based on their
                value player speed value gets handicapped via the table:
                0, -96, -128, -160, -192, -224, -256, -288
  36       1    seems to be the number of the half the player was in the game, values can be [0, 1, 2]:
                0 = didn't play or was substituted/not in starting team
                1 = started first or second half
                2 = started second half (or later)
                - these values change by the following algorithm:
                  initialized before the game starts: 0
                  at minute 1 and 46: if (value != 2) value = 1
                  at minute 45 and 90: if (value == 1) value = 2
                - they are only changed if player has less than 2 cards.
                - fresh played entering the game starts from value 0.
                - this interpretation makes sense only for players from the starting 11
  37       1    player face index, used when drawing player icon in stadium menu before the game; it gets
                initialized differently from face field at offset 5, player index is gotten via
                GetPlayerGameBreakPosition() instead of GetPlayerAtIndex()
  38      23    full name of the player, it's actually wrong during the game, since it's initialized the same
                way as previous field (luckily it's never used)

61 is the size of player structure. Players seems to be sorted by numbers
inside the file structure.

686 unknown bytes follow, which are always zero in hil files.

Seems there is some mess in the code regarding the last two fields: when drawing player sprites in the stadium
menu right before the game, players are traversed linearly from topTeamIngame and bottomTeamIngame. Face field
from offset 37 and full name from offset 38 are used. But in the game face field from offset 5 is used, and
players are iterated in a different manner: by GetPlayerAtIndex() which returns players in the order of
tactics team uses. Ingame teams end up initialized with wrong data in fields at offset 37 and 38, but it
doesn't manifest itself as they aren't used during the game.

Determines the price of the specified player.

Terminology:
- quadrant - the pitch is divided into 35 quadrants in which the ball may be
- each player has a destination quadrant to run to for each of the 35 possible
  ball quadrants

Algorithm:
- take the player's skills and pack them into one dword in this nibble order:
  ???, passing, shooting, heading, tackling, ball control, speed, finishing
- skills normally occupy half a byte (0..15), but only the lower three bits
  (value % 8) are considered when calculating the price
- for each ball quadrant:
    - unless it is in the top or bottom two rows, or is the lower central
      quadrant in front of the penalty area, determine how many players go
      there (compare where all 10 players run for the current ball quadrant)
    - use one for the excluded quadrants
    - for a CPU team, value every quadrant as 1
    - store the value in numPlayersAtQuadrant
  - use the player's destination quadrant to fetch a mask from the table; it
    packs skill weights with values from 0 to 5 into a dword

Player swapping
===============
Players in starting lineup (1-11) will keep their shirt number when swapped.
Bench players are explicitly assigned numbers 12-16, and if at least one bench
player is involved in the swap both players will swap their shirt numbers with
each other. Bench player(s) will still end up as 12-16 as SWOS will assign
those numbers to all bench players after the swap has been made.
